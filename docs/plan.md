# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 BuildLog를 FastAPI, React, Supabase와 SQLite로 개발하는 순서를 설명합니다.

한 번에 여러 Phase를 진행하지 않습니다. 각 Phase의 기능, 권한, 실패 처리를 확인한 뒤 다음 Phase로 넘어갑니다. 기능 동작이 문서와 다르면 코드를 임의로 맞추지 않고 문서를 먼저 확인합니다.

## 2. 확정한 기술 구조

| 구분 | 역할 | 기술 |
| --- | --- | --- |
| 프론트엔드 | 사용자가 보는 화면 | React, Vite, HTML, CSS, JavaScript |
| 백엔드 | API, 로그인, 권한, 데이터 처리 | Python, FastAPI |
| 데이터 접근 | 같은 코드로 두 데이터베이스 사용 | SQLAlchemy |
| 데이터 구조 변경 | 테이블 변경 이력 관리 | Alembic |
| 현재 개발 DB | 로컬 실행과 자동 테스트 | SQLite |
| 향후 서비스 DB | Supabase 수업 후 별도 연결 | Supabase Database(PostgreSQL) |
| 백엔드 테스트 | API, 권한, 데이터 규칙 확인 | pytest |
| 프론트엔드 테스트 | 주요 화면과 사용자 행동 확인 | React용 테스트 도구 |

### 역할 구분

- React는 화면만 담당하며 FastAPI API를 통해 데이터를 요청합니다.
- FastAPI는 회원가입, 로그인, 권한 검사, 기록 처리와 검색을 담당합니다.
- Supabase는 데이터베이스로만 사용합니다. Supabase Auth, Storage, Realtime은 첫 버전에 사용하지 않습니다.
- 현재 개발과 자동 테스트는 SQLite만 사용합니다.
- Supabase 연결은 관련 수업을 진행한 뒤 별도 Phase로 추가합니다.
- 향후 Supabase를 연결할 때 연결 주소와 비밀번호는 백엔드 환경 변수에만 두며 프론트엔드에 넣지 않습니다.

## 3. 개발 원칙

- `spec.md`에 없는 제품 기능은 추가하지 않습니다.
- 프론트엔드 화면과 백엔드 API의 요청·응답 형식을 먼저 맞춘 뒤 개발합니다.
- 화면에서 버튼을 숨기는 것과 별개로 FastAPI에서도 권한을 검사합니다.
- 비밀번호 원문과 비밀 설정값을 코드, 로그, API 응답에 남기지 않습니다.
- 실제 `.env`, SQLite 파일, `node_modules`, 빌드 결과와 로그는 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청 전까지 하지 않습니다.
- SQLite와 PostgreSQL의 차이를 피할 수 있는 공통 데이터 형식과 제약을 우선 사용합니다.
- 자동 테스트는 SQLite로 실행하고, Supabase 연결 검증은 별도의 통합 확인으로 진행합니다.
- Phase가 끝날 때 자동 확인과 직접 화면 확인을 모두 수행합니다.

│  ├─ alembic/               # 데이터 구조 변경 이력

│  ├─ src/

│  │  ├─ pages/              # 기능별 화면

│  │  └─ main.jsx
│  ├─ package.json
│  └─ vite.config.js

└─ .gitignore

실제 구현 중 폴더를 더 나눌 수 있지만, 위 역할과 경계는 유지합니다.

## 5. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가는 기준 |
| --- | --- | --- |
| 0 | 문서, 도구, 환경 기준 확정 | 개발을 막는 충돌과 누락이 없음 |
| 1 | 실행 가능한 FastAPI 백엔드 | 상태 확인 API와 테스트가 정상 동작 |
| 2 | 실행 가능한 React 프론트엔드 | React가 FastAPI 상태를 화면에 표시 |
| 3 | SQLite 데이터 계층 | 로컬 DB 연결과 변경 이력 테스트 통과 |
| 4 | 회원가입·로그인·닉네임 | 인증과 사용자별 접근 제한 완료 |
| 5 | 세 가지 기록의 데이터 모델 | 기본 상태와 시간·제약 테스트 통과 |
| 6 | 공부 기록 전체 흐름 | 작성·목록·검색·수정·삭제 완료 |
| 7 | 할 일 전체 흐름 | 완료 처리·필터·수정·삭제 완료 |
| 8 | 오류 기록 전체 흐름 | 해결 처리·필터·검색·수정·삭제 완료 |
| 9 | 공개 범위와 공개 검색 | 비공개 유출 없이 공개 기능 완료 |
| 10 | 댓글 | 댓글 조건과 권한 완료 |
| 11 | 좋아요 | 중복 방지와 취소 완료 |
| 12 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 조회 완료 |
| 13 | 반응형 화면과 전체 통합 | 전체 기능·권한·두 DB 호환 확인 완료 |

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 설치된 도구와 FastAPI·React·데이터베이스 구조가 서로 맞는지 확인합니다.

#### 작업

1. `MVP.md`, `PRD.md`, `spec.md`, `plan.md`의 기능 범위를 비교합니다.
2. 기술 구성이 다음과 같이 통일되었는지 확인합니다.
   - FastAPI 백엔드
   - React와 Vite 프론트엔드
   - Supabase PostgreSQL 실제 서비스 DB
   - SQLite 로컬·자동 테스트 DB
3. 첫 버전에서 제외하는 기능을 재확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
4. 설치된 Python, SQLite, Node.js와 npm 버전을 확인합니다.
5. 공식 문서를 기준으로 서로 호환되는 안정 버전을 정합니다.
6. 개발 주소를 확정합니다.
   - React: `http://localhost:5173`
   - FastAPI: `http://127.0.0.1:8000`
7. FastAPI가 React 개발 주소만 허용하도록 CORS 기준을 정합니다.
8. 환경 변수 이름을 확정합니다.
   - `DATABASE_URL`
   - `TEST_DATABASE_URL`
   - `AUTH_SECRET_KEY`
   - `FRONTEND_ORIGIN`
   - `VITE_API_BASE_URL`
9. `.gitignore`가 SQLite 파일과 생성 파일을 제외하는지 확인합니다.
10. 설치·실행·테스트 방법을 적을 `docs/setup.md`를 준비합니다.

#### 사용자에게 필요한 것

- Phase 0에는 Supabase 비밀번호나 실제 계정 값을 받을 필요가 없습니다.
- Supabase 연결 검증 전까지는 SQLite로 진행할 수 있습니다.
- 이후 Phase 3에서 실제 Supabase 연결까지 확인하려면 사용자가 만든 Supabase 프로젝트의 PostgreSQL 연결 문자열이 필요합니다.

#### 확인 방법

- 문서에 Django 템플릿을 실제 기술로 사용하는 내용이 남아 있지 않은지 검색합니다.
- Python과 Node.js 실행 여부를 읽기 전용 명령으로 확인합니다.
- Python의 `sqlite3` 모듈 사용 가능 여부를 확인합니다.
- 아직 패키지 설치, DB 생성과 애플리케이션 코드 작성을 하지 않았는지 확인합니다.

#### 완료 조건

- 기능 범위와 기술 구조의 충돌이 없습니다.
- 사용할 도구 버전, 개발 주소와 환경 변수 이름이 정해져 있습니다.
- 다음 Phase에서 설치할 항목과 실행 명령이 `setup.md`에 기록되어 있습니다.

---

### Phase 1. FastAPI 백엔드 뼈대

#### 목표

기능이 없는 상태에서도 FastAPI 서버와 자동 테스트가 실행되게 합니다.

#### 작업

1. 프로젝트 공통 `.venv`를 준비합니다.
2. FastAPI와 실행 서버, 설정 도구, 테스트 도구를 설치하고 버전을 기록합니다.
3. `backend/app/main.py`와 기본 폴더 구조를 만듭니다.
4. 서버 상태를 반환하는 `/api/health` API를 만듭니다.
5. 환경 변수에서 설정을 읽는 공통 설정 모듈을 만듭니다.
6. React 개발 주소만 허용하도록 CORS를 설정합니다.
7. API 오류 응답의 공통 모양을 정합니다.
8. 상태 확인 API의 자동 테스트를 작성합니다.
9. `.env.example`에 이름만 기록하고 실제 비밀값은 넣지 않습니다.

#### 확인 방법

- FastAPI 서버가 `127.0.0.1:8000`에서 실행됩니다.
- `/api/health`가 정상 응답을 반환합니다.
- 자동 API 문서가 열립니다.
- 테스트가 SQLite나 Supabase 연결 없이도 통과합니다.
- 허용하지 않은 프론트엔드 주소는 CORS 허용 대상이 아닙니다.

#### 완료 조건

- 백엔드 실행과 테스트 명령이 재현 가능합니다.
- 환경 변수가 없어도 안전한 개발 기본값 또는 분명한 오류가 제공됩니다.
- 회원이나 기록 기능은 아직 추가하지 않습니다.

---

### Phase 2. React 프론트엔드 뼈대

#### 목표

React 화면이 실행되고 FastAPI 상태 확인 API를 호출할 수 있게 합니다.

#### 작업

1. Vite로 React JavaScript 프로젝트를 준비합니다.
2. 화면 주소와 공통 레이아웃을 준비합니다.
3. FastAPI 호출 주소를 `VITE_API_BASE_URL`에서 읽습니다.
4. 공통 API 호출 함수와 오류 처리를 만듭니다.
5. 첫 화면에서 `/api/health` 결과를 확인합니다.
6. 기본 메뉴, 카드, 입력 폼에 사용할 CSS 구조를 준비합니다.
7. 프론트엔드 실행과 기본 테스트 명령을 문서에 기록합니다.

#### 확인 방법

- React가 `localhost:5173`에서 실행됩니다.
- React 화면에서 FastAPI 상태를 정상적으로 읽습니다.
- FastAPI가 꺼져 있을 때 사용자가 이해할 수 있는 실패 화면이 보입니다.
- API 주소나 비밀값이 코드에 직접 적혀 있지 않습니다.

#### 완료 조건

- 프론트엔드와 백엔드를 각각 실행할 수 있습니다.
- React에서 FastAPI 요청과 실패 처리를 확인할 수 있습니다.
- 제품 기능은 아직 추가하지 않습니다.

---

### Phase 3. SQLite 데이터 계층

#### 목표

SQLAlchemy와 Alembic을 사용해 내부 SQLite 데이터베이스를 연결하고 테스트할 기반을 만듭니다.

#### 작업

1. SQLAlchemy와 Alembic을 설치하고 버전을 기록합니다.
2. `DATABASE_URL`에 따라 DB 연결을 만드는 모듈을 만듭니다.
3. 로컬 개발 DB를 SQLite로 연결합니다.
4. 자동 테스트마다 독립된 임시 SQLite DB를 사용하게 합니다.
5. SQLAlchemy 모델의 공통 기본 클래스를 만듭니다.
6. Alembic이 같은 모델 정보를 읽도록 설정합니다.
7. 빈 초기 변경 이력을 SQLite에 적용하고 되돌리는 과정을 확인합니다.
8. 실제 SQLite 파일이 Git에 포함되지 않는지 확인합니다.

#### 사용자에게 필요한 것

- SQLite는 Python에 포함되어 있으므로 사용자가 제공할 값이나 별도 계정 설정이 없습니다.
- Supabase 프로젝트와 연결 문자열은 이번 Phase에서 필요하지 않습니다.

#### 완료 조건

- SQLite를 사용하는 개발·테스트 데이터 계층이 동작합니다.
- SQLite 연결, 세션, 초기 Alembic 변경 이력이 동작합니다.
- Supabase 연결은 이번 Phase의 완료 조건에 포함하지 않습니다.

---

### Phase 4. 회원가입·로그인·닉네임

#### 목표

FastAPI가 회원과 인증을 처리하고 React가 회원 화면을 제공하게 합니다.

#### 작업

1. 사용자 모델과 Alembic 변경 이력을 만듭니다.
2. 이메일·닉네임 중복과 입력 조건을 데이터 계층과 API 양쪽에서 검사합니다.
3. 비밀번호를 안전한 해시로 저장합니다.
4. 회원가입 API를 만듭니다.
5. 로그인과 현재 사용자 확인 API를 만듭니다.
6. 인증된 사용자만 사용할 수 있는 공통 권한 검사를 만듭니다.
7. 닉네임 변경 API를 만듭니다.
8. 운영자 여부를 구분할 필드를 준비합니다.
9. React 회원가입·로그인·계정 설정 화면을 만듭니다.
10. 실패 시 `spec.md`에 정한 입력값 유지와 안내를 적용합니다.

#### 완료 조건

- 회원 관련 API 테스트와 React 화면 확인이 모두 통과합니다.
- 비밀번호 원문이 DB, 로그와 API 응답에 남지 않습니다.
- 로그인하지 않은 사용자는 기록 API와 화면에 접근할 수 없습니다.
- 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

---

### Phase 5. 세 가지 기록의 데이터 모델

#### 목표

공부 기록, 할 일, 오류 기록을 SQLite와 PostgreSQL에서 같은 규칙으로 저장할 수 있게 합니다.

#### 작업

1. 공부 기록 모델을 만듭니다.
2. 할 일 모델과 완료 시간 규칙을 만듭니다.
3. 오류 기록 모델과 해결 시간 규칙을 만듭니다.
4. 모든 기록을 사용자와 연결합니다.
5. 새 기록은 기본 비공개로 설정합니다.
6. 새 할 일은 미완료, 새 오류는 미해결로 설정합니다.
7. 입력 길이와 필수값 제약을 준비합니다.
8. Alembic 변경 이력을 만듭니다.
9. SQLite 모델과 상태 전환 테스트를 작성합니다.

#### 완료 조건

- 세 기록을 SQLite에 저장하고 다시 읽을 수 있습니다.
- 기본 상태, 작성·수정·완료·해결 시간이 `spec.md`와 같습니다.
- 현재 SQLite에서 모델과 상태 전환이 정상 동작합니다.

### Phase 6. 공부 기록 전체 흐름

#### 목표

공부 기록의 작성, 목록, 상세, 검색, 수정과 삭제를 React와 FastAPI로 연결합니다.

#### 작업

1. 공부 기록 생성·목록·상세·검색·수정·삭제 API를 만듭니다.
2. API에서 작성자 권한과 비공개 접근을 검사합니다.
3. 제목과 내용의 길이·공백 규칙을 적용합니다.
4. React에 작성, 목록, 상세, 수정과 삭제 화면을 만듭니다.
5. 최신순 목록과 제목·내용 검색을 연결합니다.
6. 실패 시 입력값과 기존 저장값을 유지합니다.
7. 삭제 확인과 권한 오류 화면을 연결합니다.

#### 완료 조건

- `spec.md` 공부 기록 확인 항목이 API 테스트와 화면에서 모두 통과합니다.
- 다른 사용자의 비공개 기록은 API 직접 요청으로도 볼 수 없습니다.

---

### Phase 7. 할 일 전체 흐름

#### 목표

할 일 작성, 완료·취소, 필터, 수정과 삭제를 완성합니다.

#### 작업

1. 할 일 API와 React 화면을 만듭니다.
2. 새 할 일을 미완료·비공개로 저장합니다.
3. 미완료 우선, 같은 상태 최신순 정렬을 적용합니다.
4. 전체·남은 일·완료한 일 필터를 연결합니다.
5. 완료 시 완료 시간을 저장하고 취소 시 지웁니다.
6. 작성자만 상태 변경·수정·삭제할 수 있게 합니다.
7. 마감일, 중요도와 내 할 일 검색을 추가하지 않습니다.

#### 완료 조건

- `spec.md` 할 일 확인 항목이 API 테스트와 화면에서 모두 통과합니다.

---

### Phase 8. 오류 기록 전체 흐름

#### 목표

오류 작성, 해결·미해결 전환, 필터, 검색, 수정과 삭제를 완성합니다.

#### 작업

1. 오류 기록 API와 React 화면을 만듭니다.
2. 해결 방법 없이 미해결 오류를 저장할 수 있게 합니다.
3. 해결 방법이 있어야 해결 상태로 바뀌게 합니다.
4. 전체·미해결·해결 필터를 연결합니다.
5. 오류 제목과 오류 내용 검색을 연결합니다.
6. 해결 시 해결 시간을 저장합니다.
7. 미해결로 되돌릴 때 해결 방법은 유지하고 해결 시간은 지웁니다.
8. 작성자 권한과 삭제 확인을 적용합니다.

#### 완료 조건

- `spec.md` 오류 기록 확인 항목이 API 테스트와 화면에서 모두 통과합니다.

### Phase 9. 공개 범위·공개 기록·공개 검색

#### 목표

비공개 기록을 보호하면서 로그인 사용자에게 공개 기록을 제공합니다.

#### 작업

1. 세 기록의 공개 상태 변경 API와 화면을 연결합니다.
2. 공개 공부 기록, 할 일, 오류 기록을 한곳에 보여줍니다.
3. 종류별 필터와 각 기록의 검색 범위를 적용합니다.
4. 공개 기록을 최신순으로 보여줍니다.
5. 작성자 닉네임을 표시합니다.
6. 로그인하지 않은 요청과 비공개 직접 접근을 차단합니다.
7. 공개 목록과 검색에 비공개 기록이 섞이지 않는지 자동 테스트합니다.

#### 완료 조건

- `spec.md` 공개·비공개와 공개 검색 확인 항목이 모두 통과합니다.
- 비공개 노출 문제가 있으면 다음 Phase로 넘어가지 않습니다.

#### 목표

공개 공부 기록과 공개 오류 기록에서만 댓글을 사용할 수 있게 합니다.

#### 작업

1. 댓글 모델과 Alembic 변경 이력을 만듭니다.

6. 기록을 비공개로 바꾸면 댓글을 숨기고 재공개 시 다시 보여줍니다.

공개 공부 기록과 공개 오류 기록에서 한 사용자당 한 번만 좋아요를 남기게 합니다.

### Phase 12. 신고와 운영자 확인

#### 목표

사용자가 공개 기록과 댓글을 신고하고 운영자가 신고 내용을 확인할 수 있게 합니다.

#### 작업

1. 신고 모델과 중복 방지 제약을 만듭니다.
2. 공개 기록·댓글 신고 API와 React 입력 화면을 만듭니다.
3. 1~500자 신고 이유를 검사합니다.
4. 신고 성공과 실패 안내를 적용합니다.
5. 신고만으로 대상을 자동 삭제하지 않습니다.
6. 운영자 전용 신고 목록·상세 API와 React 화면을 만듭니다.
7. 일반 사용자의 운영자 API 접근을 차단합니다.
8. 처리 상태 변경과 운영자 직접 삭제 기능은 만들지 않습니다.

#### 완료 조건

- `spec.md` 신고 확인 항목이 통과합니다.
- 일반 사용자는 신고 자료를 볼 수 없고 운영자만 확인할 수 있습니다.

### Phase 13. 반응형 화면과 전체 통합

#### 목표

모든 기능을 컴퓨터와 휴대폰에서 사용할 수 있게 정리하고 SQLite에서 최종 확인합니다.

#### 작업

1. 공통 메뉴, 카드, 입력칸, 버튼과 안내 모양을 통일합니다.
2. 360px 이상의 휴대폰과 컴퓨터 화면을 확인합니다.
3. React의 로딩, 빈 결과와 API 실패 화면을 통일합니다.
4. FastAPI의 입력 오류, 권한 오류와 서버 오류 형식을 최종 확인합니다.
5. 백엔드와 프론트엔드 전체 테스트를 실행합니다.
6. 사용자 A, 사용자 B, 운영자 시나리오를 직접 확인합니다.
7. SQLite 테스트 전체를 통과시킵니다.
8. `.env.example`과 `docs/setup.md`를 최종 정리합니다.
9. 첫 버전 제외 기능이 추가되지 않았는지 확인합니다.

#### 최종 완료 조건

- `spec.md`의 모든 확인 항목이 통과합니다.
- React와 FastAPI를 각각 처음부터 실행할 수 있습니다.
- SQLite 자동 테스트와 전체 통합 확인이 통과합니다.
- 다른 사용자의 비공개 기록이 목록, 검색과 직접 API 요청에서 노출되지 않습니다.
- 컴퓨터와 휴대폰에서 핵심 흐름을 끝까지 사용할 수 있습니다.
- 실행 문서만 보고 다른 사람이 개발 환경을 준비할 수 있습니다.

## 7. 실제 진행 방법

1. 한 번에 Phase 하나만 진행합니다.
2. Phase의 자동 확인과 직접 확인 결과를 공유합니다.
3. 완료 조건을 충족한 뒤 다음 Phase로 넘어갑니다.
4. 문서와 다른 요구가 생기면 코드보다 문서를 먼저 수정합니다.
5. 현재 개발 범위에서는 SQLite를 사용하며 Supabase 연결은 별도 요청 전까지 진행하지 않습니다.
